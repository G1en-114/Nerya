# Agent Safety / Policy：下一阶段加分方向与开发分工

项目：Nerya Agent；战队：WayAgent FX。整理日期：2026-09-29。

本文是下一阶段的任务建议与验收契约，未标记为已有的内容均待实现。依据两份本地移植建议、评委讨论原文、Bonus Track Challenge Brief，以及当前安全实现的静态检查整理；不代表官方评分权重，也不估算涨分百分比。

## 1. 建议分工

**good person 负责后端约束、诊断与可复算收据；LoftyRain 负责用户授权、观察、停止与证据展示。**

这是按两份材料描述的经验做的任务匹配，不是假定两人都熟悉密码学。good person 的研究诊断与确定性验证经验适合解释“为什么拒绝、数据能否复算”；LoftyRain 的局部定位、状态反馈和视觉交互经验适合让用户理解并控制具体动作。签名合约沿用现有实现，涉及授权语义的变更需要集成评审。

两人的首个共同交付应该是一条完整流程：

> 用户看懂并签署限制 → Agent 提出具体动作 → 后端独立检查 → 用户看见额度与结果 → 主动停止后续动作 → 第三人从收据复核。

原有研究诊断、稳健性验证和视觉证据工作台仍有价值，但对这次安全冲刺，先接通上述流程。点头和人脸不放进 P0。

| 开发者 | P0 主任务 | 主线完成后的增强 |
|---|---|---|
| **good person** | 后端约束与安全证据：连续预算、拆单超限拒绝、停止后的执行检查、可独立运行的收据核验工具 | 研究诊断、证据版本失效检查、执行后对账 |
| **LoftyRain** | 用户控制台：看懂授权、钱包签署、观察额度、暂停／撤销、查看和导出收据 | 原图定位、字段纠错，并显示受影响的研究结论 |

## 2. 已有基础与真正缺口

| 当前基础 | 下一阶段应补的证明或能力 |
| --- | --- |
| 用户 Policy、Agent Action 的 EIP-712 签名；本地 EVM 验签 | 真人钱包完整操作；界面显示的条款与实际签名字段一致 |
| 单笔额度、同一 Policy 累计预算、nonce、期限和撤销检查 | 在一个连续会话中显示已授权额度、运行时占用、实际模拟成交及剩余额度；演示拆单也不能越过同一 Policy 总额 |
| 提交前与执行边界检查；保留 RiskGate / ApprovalGate | 从真实入口触发拒绝，证明没有下单或新增成交；错误、重试与界面刷新不会绕过 |
| 本地七案例报告、授权交易收据和事件 | 一份不依赖开发者口述、可由独立检查器复核的证据包 |
| 独立钱包签署导出页 | 授权、观察、停止、收据的连贯产品入口 |
| 已有工作区 kill switch API 与界面 | 在安全演示内接入并验收；清楚区别工作区暂停和单份 Policy 链上撤销 |
| `allowLong=false` 禁止指定范围内新开多头 | 明确当前语义；若要承诺账户净多头限制，另做仓位、待成交委托与并发预留模型 |

目前仍是 paper/mock、市价单、限定 sizing 的原型。研究建议正确与否、真实资金安全、全账户净敞口控制，不因签名存在就自动成立。

特别注意：当前累计预算按 **policy hash** 隔离。两个有效 Policy 的预算不能自动视为共享的账户总额度。修改授权时必须明确是替换还是新增；替换流程要处理旧 Policy 撤销，不能让新页面掩盖仍然有效的旧授权。

## 3. 哪些增量最能回应评委

| 优先级 | 增量 | 对应问题 | 应展示的证据 |
| --- | --- | --- | --- |
| P0 | 连续会话预算与拆单拒绝 | “Agent 拿钱以后，如何保持在边界内？” | 同一 Policy 两次允许、第三次超总额被拒；预算变化可复算 |
| P0 | 用户授权、观察、暂停与撤销闭环 | “用户到底同意了什么？如何停止？” | 钱包签名、服务端状态、停止后的新动作被拒、明确的撤销交易状态 |
| P0 | 独立收据验证 | “出了问题，第三人能查清谁授权了吗？” | 签名、plan hash、链上事件、运行时结果逐项关联；篡改后检查失败 |
| P0 | 条件变化的两轮端到端演示 | “限制真的生效，还是只有说明？” | 改预算、改允许市场后重跑，有独立 run ID 和拒绝证据 |
| P1 | 输入纠错导致旧研究／待审批建议失效 | “报告读错了，错误会不会一路变成动作？” | 更正单位后旧结论标为待重算，依赖旧版本的待执行请求被后端阻止 |
| P1 | 有界的净敞口检查 | “不要暴露 BTC 多头，能保证吗？” | 在声明的单账户单市场范围内，仓位与未完成订单共同计入，平空与反手被正确区分 |
| P1 | 执行后对账与暂停后续动作 | “运行结果偏离计划怎么办？” | 有意构造的回执差异被发现，产生事件并阻止后续动作，不能宣称撤回已成交交易 |
| P2 | 点头确认、WebAuthn、VC、ZK | 扩展交互或证明 | 等 P0 验收完成再评估，不能替代资金边界控制 |

评委原文的相关位置：约 199–219 行讨论 constraints、hallucination/hacking；269–291 行提到 AP2 与用户同意；563–572 行提出 BTC long exposure；660–680 行追问报告与来源可靠性。原文是语音转录，以上为意译。

Bonus Track B 还明确要求用户授予预算、观察支出、停止 Agent、收到收据，以及第三人依据记录重建授权关系。签名原型回应了其中一部分，完整用户流程仍需交付。

## 4. good person 的任务包

### G0：冻结接口与边界，先于两人正式接入

负责后端接口、收据模型和 reason code 的唯一归口。与 LoftyRain 用一份正常结果、一份拒绝结果、一份未知状态样例核对字段后，再各自开发。

- 复用 `nerya/security/mandates.py`、`nerya/trading/mandate_runtime.py`、`submit.py`；不创建第二套 RedLine。
- Policy、Action、domain 和 plan hash 算法保持现有定义。界面消费后端导出的 typed data，不自行重写浮点序列化。
- 明确工作区、账户、策略、Policy 四种范围；签名预算当前只约束该 Policy。
- 新增接口沿用现有控制面权限，服务端确定 owner 与操作者身份。客户端传入 `operator` 字符串不能成为认证依据。
- 暂停、恢复、重新授权均为用户／操作员控制动作。Agent 不能自行提额、关闭 kill switch 或替用户签 Policy。

### G1（P0）：把现有约束接成可查询、可操作的后端服务

复用已有校验和执行链，提供授权请求导出、签名校验、状态查询、动作结果和收据读取所需的薄接口；公开链发送与确认状态也由统一流程跟踪。接口路径以当前路由规范落地，本文不把拟议路径当成已有 API。

核心验收：

1. 同一 Policy，预算 220 USD、单笔上限 110 USD；依次申请三个 ceiling 为 101 USD 的动作。前两笔成功授权后累计为 202，第三笔因总额不足拒绝。名义单量使用可容纳模拟费用的值，例如 100 USD。余额 18 是授权余额，不是账户现金。
2. 并发请求争抢最后一份额度，实际成功总额不超过预算；重启保留本地状态后重放不会新增成交。复用已有测试，补真实入口的集成缺口。
3. 复用费用后超限、市场不允许、过期案例。对于有效期，使用确定性测试时间，避免靠现场等待。
4. 执行器创建后、成交前暂停或撤销，验证执行边界拒绝并且没有新增 fill；不能要求所有案例都“执行器数量为零”。
5. RPC 失败显示 `unknown/unavailable` 并停止受保护执行，不能显示为已撤销或已成交。
6. 单笔或多笔人工批准不能覆盖硬性 Policy 限制。对未登记账户不扩大既有签名保护声明。

预算展示至少区分：链上累计授权 ceiling、本地已认领 ceiling、模拟实际成交成本，以及观测时间／区块。当前失败动作不会自动退还已消费授权额度；不要为了让余额好看而改成无依据的自动退款。

### G2（P0）：可复算收据与独立检查器

在现有 `evidence.json` 上扩展，不另造一套报告存储。

交付一个只读检查命令：接受脱敏证据包，重新计算 Policy / Action / Plan hash、验签、核对 chain/domain/合约事件和对应请求，并输出逐项 `PASS / FAIL / UNKNOWN`。缺少成交记录时，不可推断成交成功或从未执行。

离线核验验证签名、内容绑定和记录内部一致性；在线核验才能通过指定网络核对链上记录。离线收到的 JSON receipt 本身不能证明真的上过链。执行结果仍来自可信运行时记录，链上授权不等于真实 CEX 成交证明。

拒绝证据按阶段区分：提交前拒绝记录新增 executor 为零；执行器已存在时记录提交订单／新增 fill 为零。不要直接信任一个自行写入的 `executor_called=false` 字段，必须关联持久化记录或测试调用计数。

验收至少包含：正常包通过；改金额或 plan 后失败；缺关键记录返回 UNKNOWN；重复事件不被当成两笔成交；全包不含私钥、token、Vault 内容。

### G3（P1）：发挥研究诊断优势，补错误输入与执行后检查

与 LoftyRain 联动，先支持一种证据版本改变：例如财报字段单位更正，导致依赖该字段的旧结论与待审批建议失效。后端记录依赖的 evidence ID / revision，执行前检查实际版本；不能只在前端加黄色标签。

现有 plan hash 不会自动保护外部证据版本。如果把依赖记录纳入动作，必须明确规范化字段与支持范围，并同步签名、运行时和测试；先用后端绑定的不可变依赖记录实现小范围功能也可以。重新计算后产生新动作，再走适用审批，不能偷偷修改已签名动作。

研究失败诊断／稳健性验证继续复用 `quant_research` 和 `backtest`；它们衡量研究质量，不等同于防止 Agent 越权。回测不好可以形成建议或提案，不能由 LLM 任意关闭账户或自动改策略。

执行后检查优先复用 `nerya/trading/reconciliation.py`。若增加自动暂停，触发条件、范围和恢复权限必须确定；不能把一段 LLM 诊断直接当成风控规则。

## 5. LoftyRain 的任务包

### L1（P0）：安全控制台，把用户操作连起来

在现有 dashboard 中复用审批、incidents 与钱包签名能力，做一个连贯入口；不搬入另一套前端平台。

页面至少包含四部分：

| 部分 | 用户看到和做什么 | 数据来源 |
| --- | --- | --- |
| 授权 | 账户、Agent、市场、单笔与累计额度、期限、是否允许新开多头；明确签署 | 后端生成的 typed data 和核对后的展示字段 |
| 观察 | Policy 累计授权额度、运行时占用、实际模拟成交、状态与观测时间 | G1 的服务端结果和链上查询 |
| 停止 | 工作区紧急暂停与单 Policy 撤销两个清晰操作 | 现有 kill switch 接口；owner 钱包撤销交易及确认结果 |
| 收据 | 动作、拒绝原因、来源、哈希、链记录、执行结果、导出入口 | G2 证据包，前端不自行推断结果 |

钱包签署本身不等于已上链，合约授权也不等于已执行。页面分开展示：签署状态、链上状态、Policy 判断、人工审批、执行结果。网络不可用时保留最后观测值并标记过期／未知。

复用 `/mandates/index.html` 的语义与校验，但该页面当前是独立导入／导出工具，不已有完整业务 API。钱包私钥永不进入页面表单或后端接口。

验收：真实钱包完成一次授权；错误 owner 或网络不能继续；修改条款必须重新签署；重复点击不重复执行；刷新从后端恢复；低权限用户无法执行控制动作；桌面和窄屏均能看清金额与范围。

### L2（P0）：让停止的结果准确可见

- 工作区 kill switch 会影响该工作区的相关执行，不应伪装成仅停止当前 Policy。使用隔离演示工作区，并在按钮上写清范围。
- 链上 revoke 显示待签名、已提交、已确认、失败等真实状态；点击按钮不能立即冒充确认成功。
- 接到暂停成功响应后仍要展示新动作的后端拒绝结果。成交已完成的动作保留原状态。
- 替换 Policy 时显示旧授权是否仍有效。撤销失败时不能把“新 Policy 已签署”显示成“旧额度已关闭”。
- 不承诺撤销与链下成交原子发生，也不承诺停止会自动平仓或取消所有外部订单。

### L3（P1）：原图定位与纠错，连接证据可靠性

沿用原移植建议：一种图片输入，字段定位到原图区域，保留单位、所属期、发布时间、来源、提取方式、review status 与 revision。没有可用 OCR 时允许人工标注，但明确标明。

三个样例：正常、单位歧义、模糊／缺失。字段修改后显示受影响的研究／建议，与 G3 的版本失效规则接通。截图中“忽略限制”等文本只能作为不可信内容，不能触发授权或改变工具权限。

复用 `EvidenceDoc` 与受控 Artifact Store。当前不存在 `source_type="vision"`，不能由前端直接发明；原图区域与版本字段需通过 G0 确认扩展位置。

### L4（P2）：可选点头交互

仅在已有可靠识别器且主线验收完成后做。点头只形成用户意向，最终授权仍绑定到具体请求并经过现有审批、签名与风控。摄像头故障、重复帧、内容变化都不能自动同意。

不得宣传普通点头识别等同于身份验证、活体检测或支付授权；即使用户确认，硬性禁止动作仍应被拒绝。

## 6. 两人的共享契约与文件归属

下表是新增接口的最小语义，具体命名需映射到现有模型。金额用整数 micro-USD，跨 JSON 接口宜用十进制字符串并显式转换，避免 JavaScript 大整数精度损失。

| 数据 | 至少保留的语义 | 负责人 |
| --- | --- | --- |
| 授权请求 | schema version、owner、agent、范围、市场、额度、期限、domain、完整 typed data、policy hash | good person 生成；LoftyRain 展示与签署 |
| 预算快照 | policy hash、chain authorized、local claimed、actual paper cost、授权余额、区块／观测时间、unknown 状态 | good person 计算；LoftyRain 展示 |
| 动作结果 | run ID、policy/action/plan hash、决策阶段、reason code、审批与执行各自状态、记录引用 | good person 定义并落库；LoftyRain 消费 |
| 停止结果 | scope、操作者、请求时间、后端暂停状态或 revoke tx、确认状态、已知竞态结果 | good person 接口；LoftyRain 用户流程 |
| 收据 | 前述关联数据、链 ID／合约／区块／tx、order/fill 引用、核验结果与局限 | good person 导出与核验；LoftyRain 可视化 |
| 视觉证据 | artifact / evidence ID、revision、页码区域、单位时间、质量与复核状态 | LoftyRain 提字段；good person 对齐后端与依赖检查 |

代码归属建议：

- **good person**：`nerya/security/mandates.py`、`nerya/trading/mandate_runtime.py`、相关 API 与服务、收据检查脚本、后端测试；担任集成负责人。合约尽量不变，需要修改时单独评审。
- **LoftyRain**：dashboard 页面／组件、钱包交互、原图区域展示、前端测试和英文演示素材；消费已冻结 API，不直接写授权数据库或工作区配置。
- **共享文件由 good person 合并**：Evidence schema、合约与签名结构、路由注册、共同样例和联调脚本。LoftyRain 提 schema 需求，避免双方同时改变含义。

全程保留 RiskGate / ApprovalGate，凭证走 SecretVault，模型驱动能力经 Skill 与批准脚本调用；Agent 改策略／Skill 仍走 PatchProposal。浏览器状态不成为执行依据。

## 7. 集成顺序与验收分工

不承诺“半天完成”。按可运行里程碑推进，接口／RPC／钱包兼容性出现阻塞时先解决主线。

| 阶段 | good person | LoftyRain | 退出条件 |
| --- | --- | --- | --- |
| M0 | 提供接口与真实记录样例，列现有入口与缺口 | 用样例核对界面条款、状态和失败信息 | 双方认可同一套金额、范围、状态语义 |
| M1，并行 | 完成 G1/G2 核心，连续预算与拒绝测试 | 完成 L1/L2，开发期 fixture 明确标注 | 后端与 UI 各自可检查；fixture 不当成交付证据 |
| M2，联调 | 部署选定演示网络、关联交易与运行记录 | 接真实 API、真人钱包授权／撤销、导出收据 | 一次允许、两类越界、一次停止、独立收据核验通过 |
| M3，有余力 | G3：证据版本依赖／确定性诊断 | L3：定位与纠错 | 错误字段更正后旧待执行建议确实失效 |

M2 的测试网络工作归 good person，真人签署与演示录制归 LoftyRain，由实际钱包持有人完成签名。部署所需网络、测试 gas 和 operator 配置在 M0 列为依赖。

规则原文要求 **devnet 或 testnet**，没有明确强制公共区块浏览器。现有本地 Anvil 提供本地 EVM 证据；建议最终采用可让评委独立访问的测试网或共享 devnet，并提供匹配哈希与日志。公共测试网有助于复核，但不能把它改写成规则原文唯一允许的网络。

参赛完整性另列一项：指定 Kiln NPU API / `gpt-oss-120b` 的实际工作流调用、按 flow 统计 token、能耗测量或明确假设仍需验收。good person 归口工作流接入和用量产物，LoftyRain 展示；先复用已有 provider 配置，不在本次分析中假定已接通。离线自动测试使用 fake transport，真实服务验收另做并明确标记。

## 9. 给评委的展示顺序

1. **用户问题**：希望 Agent 执行有限授权，同时能知道额度去向并随时阻止后续动作。
2. **签署**：真人钱包确认市场、额度与期限；屏幕解释签名具体覆盖什么。
3. **允许**：一次合规 paper 动作走到成交，展示链上授权和模拟回执的对应关系。
4. **两类停止**：费用后超限、改变允许市场；记录原因与未执行证据。连续拆单预算作为可展开案例。
5. **用户控制**：暂停工作区或撤销指定 Policy，再发新动作看到后端拒绝。
6. **独立复核**：导出收据，另一人运行检查器；改一个金额后验证失败。

完成对应验收后可使用的英文讲法：

> The user signs a bounded policy. Our runtime independently checks each proposed action, including costs and the remaining authorization budget. The user can monitor activity and stop subsequent execution. We export the signed authorization, chain records, and runtime receipts so another person can inspect how the decision was made. This demonstration uses paper trading; a chain authorization is not proof of a live exchange fill.

如果 P1 也完成，可以补充：

> When a source field is corrected, dependent recommendations become stale. A pending action tied to the old evidence must be revalidated before it can proceed.

不使用“保证不亏”“所有日志不可篡改”“完整 AP2”“跨账户全局 exactly-once”或预估涨分数字。
